kik Documentation

kik is a local-first planner. It compiles a Korean sentence into an executable plan, calls tools deterministically, asks a local LLM only for judgment and wording, and performs writes only after you approve them.

Introduction #

Most assistants let the model choose tools and act immediately. kik separates those decisions: a parser and a rules compiler produce a plan, the plan fixes which tools run and in what order, and the model is reserved for judging evidence and writing the final sentence.

The result is a thin JSON envelope the client can render, confirm, or reject. Nothing is written to a calendar before a human approves it, and the same approval is idempotent.

  • Model: one local model (Qwen3-4B) on llama.cpp, no cloud calls.
  • Tools: fixed by the plan, not selected by the model.
  • Writes: approval-gated and idempotent.
  • Output: a small JSON envelope, not prose to parse.

Get started #

kik runs as a long-lived server on a Linux host and a small desktop client on macOS. The server boots a C++ daemon on llama.cpp, a Node API, and three sidecars. The client speaks only to the API.

The source repository is private. This page and its git history are public; the design notes below describe the shipped behaviour and measured numbers.

Requirements

  • Linux host with llama.cpp (Vulkan or Metal) and a 4B-class model.
  • Node 26 for the API and sidecars.
  • macOS with Tauri 2 for the client.

One request

POST /plans
{
  "message": "If the weather is nice tomorrow evening, add a walk.",
  "location": "Gangnam-gu",
  "lat": 37.4979,
  "lon": 127.0276,
  "now": "2026-10-23T09:03:00+09:00"
}

The response is a plan plus a final envelope:

{
  "state": "waiting_confirmation",
  "envelope": {
    "v": 1,
    "plan_id": "p-mvk4wo9p-4fb06456",
    "kind": "confirm",

    "requires_confirmation": true,

}

Architecture #

The boundary is the process. The daemon owns the model; only the CLI talks to its Unix socket; the API runs the CLI and owns the public HTTP contract.

ProcessRoleBoundary
kik-daemonC++23 on llama.cpp. Models, contexts, KV cache, inference.Unix socket only
kik-cliThin command client; the only daemon speaker.Unix socket
kik-apiNode 26 + Fastify. /plans, tools, timelines, confirm tokens.HTTP on the LAN
kik-parserdmecab-ko sidecar. Morphology, clause tags, slots.Loopback HTTP
kik-clientTauri 2 + Svelte 5. Frameless input, logs, result card, tray.API only

Plans #

A plan is a small typed tree. The compiler builds it from parser output and rules; the executor walks it in order.

NodeMeaning
seqRun steps in order.
ifConditional branch, usually a weather condition.
callDeterministic tool call with typed arguments.
judgeOne LLM judgment over evidence, with a JSON schema.
finalWrites the user-facing message in a 4k context.
confirmApproval gate before a write.
askMissing slot; stops before execution.

Relative time

The client sends now with every request. The compiler resolves tomorrow, this evening and similar expressions against it in KST, so the reference time is the user's, not the server's. If a time cannot be resolved, the plan is an ask, not a guess.

Missing slots

When a required slot is absent the plan never executes. The API returns kind: "ask" with the missing field names, and the client asks the user instead of inventing a place or a time.

Final envelope

The model writes only {"message": string}. The server assembles v, plan_id, kind, action, confirm_token and state. A model cannot fabricate a token or change the state machine.

Tools #

Tools are ordinary code with typed inputs, timeouts and error codes. The model never picks one.

ToolInputNotes
weather.forecastlocation, at, optional lat/lonKMA grid. City table or Lambert conversion from coordinates.
calendar.availabilityat, duration_minReads local SQLite for overlapping events.
calendar.createtitle, start, duration_minOnly on confirm; idempotent per plan.

Approval

Before approval, the calendar write count is zero. Confirming once writes exactly one row; confirming again returns the same event instead of duplicating it. If the slot is already taken, kik answers with the conflict instead of offering a confirmation.

Unknown places

An unknown location is not a server error. The API returns an ask with missing: ["location"], and the client lets the user correct it. The client geocodes a name once, stores the coordinates, and sends them with later requests.

Client #

The macOS client is a frameless window anchored to the bottom-right: a log panel, an optional result card, a location row, and the composer. It renders envelopes and never defines them.

  • A location row stores a name and its coordinates once; each request carries now and the coordinates.
  • The result card shows the message and, for confirm, the action with approve and cancel.
  • A menu bar icon can show the window or reset its position.

Performance #

Measured on the reference host: Qwen3-4B-Instruct IQ4_NL on CPU, one request at a time, one lane per role.

StageTimeThroughput
Parse0.01 s—
Weather (KMA)1.7 s—
Judge (16k context)2.2 s23.7 tok/s
Final (4k context)3.5 s21.1 tok/s
One plan, end to end6.8–8.1 s—

Two lanes are worse on this host: CPU contention drops throughput to roughly 11 tok/s, so the default stays at one. The fast case is not the only case reported here.

The 16k judge and 4k final contexts are reused between plans and reset after each request. Shared multi-sequence batching (seq_id) is not implemented in the daemon yet; the current gain comes from context reuse and measurement, not batching.
